TOUCH-AND-HOLD FLASHLIGHT WEBSITE
Complete Phase-Wise Implementation Plan
Goal: A mobile-first website where the device flashlight/torch stays ON only while the user keeps touching/pressing the main button, similar to a bike horn. When the finger is released, the flashlight turns OFF.
1. Important Technical Reality
A normal website cannot guarantee direct flashlight control on every browser/device. Modern mobile browsers expose the torch through camera-related APIs only on supported devices/browsers. The implementation should therefore detect support and provide a clear fallback.
The web app must run over HTTPS (localhost is also suitable during development).
Torch control generally requires camera access; the browser may show a camera permission prompt.
Permission cannot legally/technically be pre-granted by JavaScript. The browser/OS controls permissions.
The best user experience is to request the required permission once during a dedicated Setup/Enable Torch action, then remember the browser's granted state.
Do NOT ask for permission repeatedly on every touch. Initialize the camera stream once and reuse it.
On supported browsers, the torch can be controlled through the camera MediaStreamTrack's torch constraint.
Some browsers/devices do not expose torch control to websites. For those, show an unsupported-device message instead of pretending it works.
2. Recommended Technology Stack
Frontend: HTML5 + CSS3 + JavaScript (Vanilla JS)
Mobile UI: Responsive CSS, large touch area, touch-action: none
Torch access: MediaDevices.getUserMedia() + MediaStreamTrack.applyConstraints({advanced:[{torch:true/false}]}) where supported
Input handling: Pointer Events: pointerdown, pointerup, pointercancel, pointerleave
Permission flow: One-time Setup/Enable Torch button triggered by user gesture
Persistence: localStorage for app state/preferences; permission itself remains controlled by browser
PWA: Web App Manifest + Service Worker for installable app-like experience
Hosting: HTTPS hosting such as GitHub Pages, Netlify, Vercel, or similar
Optional native upgrade: Android native wrapper/app if true hardware-level reliability is required
3. User Experience Flow
1. Open website.
2. First visit: show a Setup screen explaining that camera permission is needed only to access the supported device torch.
3. User taps “Enable Flashlight” once.
4. Request camera permission using getUserMedia().
5. Detect the video track's torch capability.
6. If supported, keep the camera stream alive but do not turn torch on yet.
7. Show the main HOLD TO FLASH button.
8. User presses and holds the button → torch ON.
9. User releases the button → torch OFF.
10. If touch is cancelled/interrupted → immediately turn torch OFF.
11. When the page is hidden/closed → stop torch and release the camera stream.
4. Phase 0 — Requirements & Scope
Define the MVP before coding:

No repeated permission prompt during normal use.
Mobile-first interface.

No unnecessary camera preview on the main screen.

6. Phase 2 — Permission & Torch Initialization
Create a single initialization function. It should run only from the user's explicit Setup/Enable button. Store the MediaStream and video track in memory.
Core logic (conceptual):
let stream = null;let track = null;let torchSupported = false;async function initTorch() {  stream = await navigator.mediaDevices.getUserMedia({    video: { facingMode: { ideal: "environment" } },    audio: false  });  track = stream.getVideoTracks()[0];  const caps = track.getCapabilities ? track.getCapabilities() : {};  torchSupported = !!caps.torch;  if (!torchSupported) {    stopCamera();    throw new Error("Torch is not supported by this browser/device.");  }}
Important: getUserMedia permission is controlled by the browser. JavaScript cannot silently pre-approve it. The correct strategy is one explicit setup action, followed by reusing the same stream during the session.
7. Phase 3 — Touch-and-Hold Flashlight Logic
Use Pointer Events instead of separate touch/mouse handlers. This gives a consistent model for finger, stylus, and mouse input.
async function setTorch(on) {  if (!track) return;  await track.applyConstraints({    advanced: [{ torch: on }]  });}button.addEventListener("pointerdown", async (e) => {  e.preventDefault();  button.setPointerCapture?.(e.pointerId);  await setTorch(true);});async function releaseTorch(e) {  e?.preventDefault();  await setTorch(false);}button.addEventListener("pointerup", releaseTorch);button.addEventListener("pointercancel", releaseTorch);button.addEventListener("lostpointercapture", releaseTorch);
Use a boolean such as isPressed to prevent duplicate ON/OFF calls. Always handle pointercancel/lostpointercapture because calls, scrolling, browser interruptions, or finger movement can otherwise leave the torch state inconsistent.
8. Phase 4 — UI/UX Design
Full-screen dark interface.
Large central circular/rounded HOLD TO FLASH button.
Button visual state: OFF → Ready; pressed → FLASH ON.
Small status text: “Torch ready”, “Press and hold”, “Release to turn off”.
Setup button shown only until initialization succeeds.
Prevent accidental page scrolling while pressing the main button using touch-action: none.
Do not make the button dependent on a tiny area; use a large touch target.
Optional vibration feedback can be added with navigator.vibrate() where supported.
9. Phase 5 — Permission Strategy (No Repeated Asking)
Target behavior:
First setup: ask once.
After permission is granted: reuse the active stream; do not call getUserMedia() for every press.
After page reload: the browser may retain the permission decision, but the app must request a new stream because the old stream no longer exists. This is a new API call, not a new permission prompt if the browser has retained permission.
If the user blocks permission, show instructions to change camera permission in browser site settings.
Never attempt hidden camera access, permission bypasses, or automatic permission grants.
Note: 'Give all permissions in advance' is not technically possible for a website. The browser/OS owns permission controls. The implementation can minimize prompts, but cannot override them.
10. Phase 6 — Safety & Lifecycle Handling
Before page becomes hidden: turn torch OFF.
On beforeunload/pagehide: stop track and release camera resources.
On errors during applyConstraints(): set UI to OFF and show a non-blocking error.
If the stream ends unexpectedly, disable the main button and require re-initialization.
Never leave torch ON intentionally after the user releases the button.
Do not expose or upload camera frames; only use the MediaStream locally for torch access.
11. Phase 7 — PWA Implementation
Add manifest.webmanifest with name, short_name, icons, theme_color and display: standalone.
Add a service worker for caching the app shell.
Provide an Install App option where supported.
Keep torch logic in the page JavaScript; the PWA itself does not bypass browser hardware restrictions.
Test both installed-PWA mode and normal browser mode because permission behavior can differ by platform.
12. Phase 8 — Testing Matrix
First visit: Setup prompt appears; user explicitly enables camera access.
Permission granted: Torch capability is detected; main button becomes active.
Press and hold: Torch turns ON and remains ON while pressed.
Release: Torch turns OFF immediately.
Quick tap: Torch briefly turns ON then OFF.
Pointer cancel: Torch turns OFF.
Finger leaves button: Torch turns OFF.
Screen/page hidden: Torch turns OFF and resources are released.
Permission denied: Clear instructions are shown; no endless permission loop.
Unsupported torch: Main control disabled with browser/device compatibility message.
Repeated presses: No repeated permission prompt in the same permission state.
Reload: App reinitializes cleanly; no stale stream is reused.
13. Phase 9 — Browser/Device Compatibility Strategy
Do not assume that every Android/iPhone browser exposes torch control. Build a feature-detection path instead of relying only on browser name.
Check navigator.mediaDevices and getUserMedia availability.
Check the returned video track and getCapabilities().torch.
If torch is unavailable, show “Flashlight control is not supported in this browser/device.”
Test on the actual target phones before publishing the compatibility promise.
If the project must work reliably on a wide range of Android phones, consider a native Android app or trusted native wrapper.
14. Phase 10 — Native Android Option (If Website Limitations Are Not Acceptable)
If the real requirement is guaranteed hardware flashlight control with minimal browser restrictions, the final product should be an Android app rather than a pure website.
Android: Kotlin + Android Camera2/CameraX or appropriate torch API.
Use CameraManager.setTorchMode() where supported.
Request only the permissions actually required by the chosen implementation.
Keep a foreground touch interaction: ACTION_DOWN → torch ON; ACTION_UP/ACTION_CANCEL → torch OFF.
A WebView-based app can host the website UI, but native code should control the flashlight if hardware reliability is the priority.

17. Definition of Done
The user performs one explicit setup action for permission.
The app does not request permission on every press.
Holding the main button keeps the torch ON.
Releasing the button turns it OFF.
Pointer cancellation and page lifecycle always turn it OFF.
Unsupported devices are detected gracefully.
The site is served over HTTPS.
The PWA can be installed where supported.
Real-device tests are completed on the intended Android/iOS browser targets.
If guaranteed hardware behavior is required, the native Android option is implemented.
18. Key Decision
For the first version, build a mobile-first HTTPS PWA using HTML/CSS/JavaScript and MediaStreamTrack torch control with feature detection. Do not design the system around repeated permission prompts. Initialize once, reuse the stream, and switch the torch only from pointer press/release events. If the target phone/browser does not expose torch control, move the flashlight-control layer to a native Android app.
